# 8.1.3 Upstox v3 Historical API Integration Migration Plan

## Overview
This document outlines the migration from 1-minute to 5-minute candle ingestion using Upstox v3 historical APIs, focusing on removing 1-minute batch ingestion while maintaining database support and implementing direct 5-minute candle ingestion with indicator calculation and storage.

## Current State Analysis

### Existing Architecture
- **Upstox API Client**: `/upstox/go_api_client/` - Swagger-generated client for v3 APIs
- **Authentication Service**: `/internal/core/adapters/client/upstox/auth_service.go` - Handles API authentication and rate limiting
- **Batch Fetch Service**: `/internal/service/batch_fetch_service.go` - Manages batch processing with 4-day intervals
- **Candle Processing**: Multiple services for 1min ingestion and 5min aggregation
- **Database Schema**: Separate tables for 1min and 5min candle data

### Current API Endpoints
1. **Batch Historical Data Ingestion**:
   - `POST /historical-data/batch-store` - Currently processes 1min candles
   - Handler: `BatchStoreHistoricalData` in `server.go`
   - Interval validation: `1minute 5minute 30minute day week month`

2. **Individual Historical Data Retrieval**:
   - `GET /historical/{instrument}/{interval}/{to_date}/{from_date}`
   - Direct Upstox API proxy for historical data retrieval

### Current 1-Minute to 5-Minute Flow
1. **1-Minute Ingestion**: Batch fetch service ingests 1min candles from Upstox API
2. **Aggregation Trigger**: After 1min ingestion, system triggers 5min aggregation
3. **Storage**: Both 1min raw data and 5min aggregated data stored separately
4. **Indicator Calculation**: Technical indicators calculated during aggregation

## Problem Statement

### Issues with Current Approach
1. **Unnecessary 1-Minute Ingestion**: System ingests 1min data only to aggregate to 5min
2. **Resource Waste**: Double storage and processing overhead
3. **API Rate Limiting**: More API calls required for 1min data
4. **Complexity**: Multi-step process increases failure points
5. **Maintenance Burden**: Need to maintain both 1min and 5min data pipelines

### Upstox API Constraints
- **Historical Data Limits**: 1minute: last 1 month, 5minute: last 1 year
- **Rate Limiting**: 2 requests per second for historical data
- **Batch Size**: 4-day intervals for optimal performance (as configured)

## Requirements

### Primary Requirements
1. **Remove 1-Minute Ingestion**: Eliminate 1min batch ingestion from batch service
2. **Maintain DB Support**: Keep 1min database schema and repository for future use
3. **Direct 5-Minute Ingestion**: Implement direct 5min candle ingestion from Upstox API
4. **Indicator Calculation**: Calculate technical indicators for 5min candles
5. **Storage Optimization**: Store calculated indicators with 5min candles

### Secondary Requirements
1. **Backward Compatibility**: Existing API endpoints should continue working
2. **Performance**: Maintain or improve ingestion performance
3. **Error Handling**: Robust error handling and retry mechanisms
4. **Monitoring**: Comprehensive logging and monitoring

## Solution Approaches

### Approach 1: Direct 5-Minute Ingestion (Recommended)
**Description**: Modify batch fetch service to directly ingest 5-minute candles from Upstox API

**Advantages**:
- Reduced API calls (1/5th of current volume)
- Simplified processing pipeline
- Lower storage requirements
- Faster ingestion process
- Better API rate limit utilization

**Implementation**:
- Update `BatchFetchService` to support direct 5min interval processing
- Modify Upstox API client calls to use `5minute` interval
- Update indicator calculation to work with 5min timeframe
- Implement validation for 5min candle boundaries

### Approach 2: Hybrid Approach
**Description**: Maintain both 1min and 5min ingestion capabilities with configurable selection

**Advantages**:
- Flexibility for different use cases
- Gradual migration capability
- Fallback option available

**Disadvantages**:
- Increased complexity
- Maintenance overhead
- Resource utilization not optimized

### Approach 3: External Aggregation Service
**Description**: Create separate microservice for candle aggregation

**Advantages**:
- Service separation
- Scalability

**Disadvantages**:
- Added system complexity
- Network overhead
- Deployment complexity

## Recommended Design

### Architecture Changes
```
Current Flow:
Upstox API (1min) → Batch Service → 1min Storage → Aggregation → 5min Storage

Proposed Flow:
Upstox API (5min) → Batch Service → Indicator Calculation → 5min Storage
```

## Risk Assessment

### High Risk Items
1. **Data Inconsistency**: Direct 5min vs aggregated 5min data might differ
   - **Mitigation**: Comprehensive validation and testing
   - **Rollback**: Revert to 1min aggregation if needed

2. **API Rate Limiting**: Changes in API usage patterns
   - **Mitigation**: Monitor rate limits closely during migration
   - **Rollback**: Reduce batch sizes if rate limits exceeded

3. **Indicator Calculation Changes**: 5min direct vs aggregated indicators
   - **Mitigation**: Parallel calculation and comparison during transition
   - **Rollback**: Use aggregated calculation as fallback

### Medium Risk Items
1. **Performance Impact**: Changes in ingestion performance
2. **Client Compatibility**: Existing API clients expecting 1min data
3. **Data Storage**: Potential increase in 5min data volume

### Low Risk Items
1. **Database Schema**: 1min schema preservation
2. **Upstox API Compatibility**: Well-established v3 API
3. **Error Handling**: Existing robust error handling framework
